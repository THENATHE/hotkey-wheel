# Hotkey Wheel audit and upstream refresh, 2026-11-08

Scope: every source file under `src/main`, the QA harness in `qa/`, build metadata, and each Buildprint and Tool Pouch class or member the wheel uses. The audit compared the decompiled Buildprint 0.1.19 and 0.1.38 and Tool Pouch 1.1.10 and 1.2.0 developer releases. Original upstream JARs were not modified. The audit produced 1.0.9+26.3, which was packaged but never published. A follow-up fix chosen by the user makes the release 1.0.10+26.3.

Loader 0.20.1 exists, but the user's profiles and Vanilla++ still run 0.19.5, and the wheel's `>=0.19.5` requirement accepts both. The `fabric-api >=0.161.0` requirement is kept: the source still compiles against 0.161.0, and it compiles against Buildprint 0.1.19 and Tool Pouch 1.1.10 too.

## API review

Buildprint 0.1.38 keeps every signature the wheel calls: `BuildprintEditor.isActive/open/close/isEditorScreen/addListener`, `EditorListener.onEnter/onExit` and `BuildprintHud.hideWhile`. The only addition is `isAvailable()`, which the wheel does not need. The control names `key.buildprint.open` and `key.buildprint.editor` and the classes `BuildprintScreen` and `MaterialListScreen` are unchanged. Behavior changes that matter to the wheel:

- The editor's raw key handler now also consumes C (camera), the Drop and Inventory keys (step tool), Backspace and Escape, plus Enter, Ctrl+Z, P, R, N and the arrow keys in some tools. In 0.1.19 it consumed only Delete, `[`, `]`, H, Tab and the digit keys.
- `open()` can show a one-time camera choice dialog (free or walking camera) and return false. Singleplayer worlds default to free camera, so no dialog appears there. On multiplayer servers Buildprint asks the first time for each server.
- The editor can run from the player's own camera (walking mode) without freecam.
- The Save tool moved from toolbar number 3 to number 4, and the loaded-schematic list now groups rows into sections.

In Tool Pouch 1.2.0, `ContextualSelectionWidget`, `ModKeybinds.OPEN_WIDGET`, `ScrollHandler`, the three payloads, `MultiLoaderUtil`, `GameplayUtil.isHoldingProjectileWeapon/getSupportedAmmo` and `ToolPouchUtil.getItemsFromToolPouch` all keep their signatures. The new disabled-slot feature removes disabled slots from `getItemsFromToolPouch`, and the server's shulker lookup skips them too. Because the wheel uses that same list, its indices still match the server's.

## Fixed

1. **The original opener could not close a wheel-owned editor when its key is one Buildprint 0.1.38 now reserves**, for example C or E. Buildprint's order-1000 keyboard handler consumed the key first. This is the keyboard version of the 1.0.8 side-mouse bug. `KeyboardMixin.java:18` adds an order-900 injector that only runs the owned-menu return (`HotkeyWheelClient.handleMenuReturn`, `HotkeyWheelClient.java:63`). Opening wheels and every other wheel key keep their ordinary order, so Buildprint's editor shortcuts still behave natively unless the wheel owns the session. The shipped 1.0.8 JAR fails the new regression with Buildprint 0.1.38: `qa/regressions/1.0.8-upstream-2026-11/shipping-1.0.8-reserved-keys/`.
2. **Building from Modrinth Maven fetched the NeoForge Tool Pouch.** `maven.modrinth:tool-pouch:1.2.0+26.3` resolves to `toolpouch-neoforge-1.2.0+26.3.jar`. Compilation still passed because the classes the wheel uses have the same names. `build.gradle:28` and `build.gradle:33` now pin Modrinth version IDs, and the resolved hashes match the published Fabric files.
3. **An unreadable `hotkey-wheel.json` could be lost.** Loading kept the file but used defaults, so the next Save replaced the user's wheels and remembered keys. `WheelConfig.java:77` now copies an unreadable file to `hotkey-wheel.json.unreadable` before anything can replace it. A readable file loads exactly as before. The shipped 1.0.8 JAR fails only this new check: `qa/regressions/1.0.8-upstream-2026-11/shipping-1.0.8-config/`.
4. **Per-frame lookups in the radial.** Each frame, the radial searched every registered key mapping and created a new icon stack for every slot. `WheelScreen.java:58` now resolves icons and controls once when the wheel opens or switches. What is drawn does not change.
5. **Metadata.** `fabric.mod.json` suggested exactly `toolpouch 1.1.10`. It now suggests `>=1.1.10`.
6. **Wheel-opened editor on a server's first camera question (1.0.10).** Buildprint's `open()` returns false while its one-time camera question is shown, and 1.0.9 dropped its claim. The editor started from the answer then could not be closed with the wheel opener. `BuildprintApiIntegration.java:108` now keeps the pending claim. `BuildprintEditorReturn.java:53` extends it while that exact question is open, and `BuildprintEditorReturn.java:80` lets the original opener close the question. The unpublished 1.0.9 JAR fails the new dedicated-server fixture: `qa/regressions/1.0.9-server-camera-question/`.

## QA harness changes

- `qa/run.py` defaults to Buildprint 0.1.38, Blocktone 0.1.38, Vanilla++ 1.5.0, BRBR 1.11.8 and Polymer 0.18.7. `HOTKEY_WHEEL_BUILDPRINT_JAR` and `HOTKEY_WHEEL_TOOLPOUCH_JAR` select exact inputs. `--toolpouch` adds a profile with standalone Tool Pouch, because Vanilla++ 1.4.5 still bundled 1.1.10. Vanilla++ 1.5.0 bundles Tool Pouch 1.2.0, and the runner reads the bundled version from the suite JAR. `--no-blocktone` checks a Buildprint release before its matching Blocktone build exists; Blocktone 0.1.25 requires exactly Buildprint 0.1.25. Release packaging still requires the full Blocktone profile.
- The client gametest module is matched to the profile's Fabric API instead of a hard-coded 6.0.7 build.
- Every run clears the isolated game's mod `config/` directory. A failed run had saved Buildprint's walking-camera choice, and the next run inherited it.
- Runs work on Xvfb. SDL's GLX path cannot load Xvfb's Mesa GL, so the runner defaults `SDL_VIDEO_FORCE_EGL=1`. Rendering on Xvfb uses Mesa's software renderer.
- New checks: reserved-key openers C and E close a wheel-owned editor; walking-camera editor ownership and closure; a 1.0.8 configuration loads and saves with every field, absent-mod slot and remembered key intact and no key binding changes; an unreadable configuration is copied aside; Tool Pouch disabled slots are left out of the radial and the next shulker still opens; tool numbering is read from Buildprint's registry. The BuildPrint 0.1.25 fixture changes are carried over (KitButton clicks, VoxelSprout settings screen).

## Not changed

- **Wheel keys inside the editor.** Buildprint's reserved editor keys still win over opening a wheel while the editor is active, as documented since 1.0.7. Only the original opener of a wheel-owned session takes precedence.
- **Fabric Loader 0.20.1** is not adopted, for the reasons above.
- **Icon picker tiles** still create an item stack per frame. Caching them across a world change could show stale item data, and the picker is an editor screen, not a gameplay hot path.
- The older Buildprint fallbacks (0.1.16–0.1.18 reflection) stay unchanged and were not retested in this release.

## Data compatibility

The settings schema in `config/hotkey-wheel.json` is unchanged. The new QA check loads a 1.0.8-format file with every setting changed from its default, then saves it, and verifies identical JSON. The shipped 1.0.8 JAR passes the same load and save checks, which confirms the fixture matches 1.0.8. Key names in `options.txt` are unchanged, and loading never changes Minecraft key bindings.
